[1편]({{ site.baseurl }}/posts/Gemma-4-Developer-Agent-From-Issue-to-Verified-Patch-KR/)의 에이전트는 이슈를 읽고, 저장소에서 코드를 찾아 고친 뒤, 패치를 검증받는다. 한 달 동안 실행해 보니 이 과정의 여러 곳에서 실패가 생겼다. 어떤 실행은 소스를 고치기도 전에 멈췄고, 어떤 실행은 패치를 만들었지만 테스트를 통과하지 못했다. 그 사이 주최 측이 배포한 실행·채점 소프트웨어도 바뀌었다. 점수가 달라졌을 때 에이전트의 개선 때문인지 알려면, 실행 기록과 채점 조건을 함께 확인해야 했다.

실행 기록과 제출 결과에서 확인한 차이는 다음과 같다.

1. **같은 도구 호출을 반복하기 시작하면 좀처럼 빠져나오지 못했다.** 공개 과제 22개를 비교한 실험에서, thinking을 끈 에이전트가 호출 하나를 보낸 뒤 똑같은 호출을 한 번 더 보낼 확률은 0.056이었다. 이미 같은 호출을 세 번 이상 연속해서 보낸 구간에서는 다음에도 같은 호출을 보낼 확률이 0.97이었다. 모든 호출에 같은 반복 확률을 적용해서는 이 차이를 설명하기 어렵다. 다만 이 곡선만으로 반복의 원인까지 알아낸 것은 아니다.
2. **context 한도에 걸린 이유는 토큰 수로 확인할 수 있었다.** 한 실행에서는 같은 호출이 55번 나온 뒤 다음 요청이 거부됐다. 첫 호출을 한 번으로 세고 이후의 반복을 계산하면, 54번을 더 할 수 있다는 계산이 실제 기록과 맞았다.
3. **같은 패키지를 제출해도 호스트 점수가 달랐다.** 파일이 바이트 단위로 같은 패키지가 0.10과 0.15를 받았다. 두 제출은 공개 파일의 변경 시점을 기준으로 같은 host epoch에 분류한 결과다. 실제로 확인한 점수 차이다. 하지만 두 결과만으로 일반적인 점수 변동 폭이나 구별할 수 있는 최소 개선량을 추정할 수는 없다.
4. **과제를 잘 푸는 것과 제한 시간 안에 끝내는 것을 함께 봐야 했다.** 12시간을 넘기면 제출 전체가 오류로 끝난다. 느린 에이전트가 개별 과제를 더 잘 풀더라도, 전체 실행을 끝내 점수를 받을 가능성은 낮아질 수 있다. 로컬 실행 시간으로 이런 위험을 살펴볼 수는 있지만 비공개 채점 서버에 시간이 얼마나 남을지는 알 수 없다.

비교 기준으로 삼은 **E0052는 공개된 [Budget-Fit single-agent 패키지][budget-fit]**다. 설정과 프롬프트를 묶은 이 패키지는 원저자를 밝히고 그대로 사용했다. 1편의 채점받지 않은 실습 예제나 초기 도구 오류를 조사할 때 쓴 recovery 패키지와는 다르다. 기록한 최고 Public 점수는 **0.18**이며, 비교한 변형 중 이를 넘은 것은 없었다. 과제 구성, 실행마다 생기는 변동, runtime의 영향이 각각 얼마나 큰지는 이 점수들만으로 구분할 수 없다.

**2026년 10월 23일(KST)까지 확인한 기록**이다. 날짜가 붙은 리더보드 스냅샷과 과거 비교는 당시 조건을 따른다. **10월 23일 09:01 KST**에 낸 E4B 제출은 이 기록에서 아직 대기 중이며 성능 결과는 없다. 본 대회 마감은 **12월 2일 23:59 UTC(한국 시간 12월 3일 08:59)**다.

## 1. 바뀌는 채점 환경을 어떻게 구분했나

주최 측은 에이전트를 실행하고 패치를 채점하는 Python 패키지들을 wheelhouse로 배포한다. 이 안의 vLLM은 모델 응답을 생성하고, harness는 모델이 요청한 도구를 실행하며, verifier는 최종 패치에 테스트를 적용한다. 이 소프트웨어와 실행 설정을 포함한 환경을 runtime이라고 부른다. 어느 부분이 바뀌었는지에 따라 같은 패키지의 결과도 달라질 수 있다. 9월 25일 이후 주최 측은 wheelhouse를 열 번 더 올렸고, 데이터를 다시 배포했으며, 답변을 기다리던 질문에도 답했다.

한 팀이 동시에 대기시킬 수 있는 제출은 하나뿐이다. 채점이 시작되기까지 대략 14–33시간을 기다린 경우도 있었다. 그 사이 환경이 바뀌면, 제출 당시 공개된 파일이 실제 채점에도 쓰였는지 단정하기 어렵다.

점수에는 제출한 번들 $b$와 함께, 관찰한 환경의 기간 $e$를 붙여 $S_e(b)$로 기록했다. **host epoch**는 공개 파일이 바뀐 시점을 기준으로 나눈 기간이다. 문서만 달라졌을 수도 있고 실행 코드까지 달라졌을 수도 있으므로, epoch가 다르면 우선 무엇이 바뀌었는지 확인한다. 같은 epoch에 속하더라도 비공개 서버의 모든 실행 조건이 같았다고 보장되지는 않는다.

제출 시각부터 점수를 처음 확인한 시각까지를 $[t_s, t_c]$, epoch $k$의 시작으로 삼은 산출물이 공개된 시각을 $b_k$라고 하자. 채점 서버에 적용된 실제 시각은 알 수 없으므로, 공개 뒤 6시간의 여유 $\delta$를 두고 다음 조건을 만족하는 점수만 epoch $k$에 배정했다.

$$
b_k + \delta \le t_s \quad\text{and}\quad t_c < b_{k+1}.
$$

배포가 반드시 6시간 안에 끝난다는 측정 결과는 없다. 점수를 보수적으로 분류하기 위해 정한 규칙이다. 이 조건에 맞지 않는 점수도 보관하지만 번들 간 직접 비교에는 사용하지 않는다.

이렇게 나누면 9월 23일부터 10월 13일까지 11개 epoch가 된다. 비공개 채점기가 실제로 열한 번 달라졌다고 확인한 것은 아니다. 마지막 경계도 파일의 timestamp가 새로 만들어진 것을 보고 설정했다. 이후 비교에서는 bulk 파일 507개가 바이트 단위로 같았고 새 과제 내용도 없었다. 앞서 공개된 README는 우리가 보관하던 이전 사본과 달랐다.

패키지 버전 번호가 같아도 파일이 같다는 뜻은 아니다. 주최 측은 10월 12일 `swegemma 0.2.11`과 vLLM 0.19.1을 버전 번호를 바꾸지 않고 다시 빌드했다. 그래서 로컬 평가에는 실제 파일의 hash를 남긴다. 서버 명령, 패키지 digest, 데이터 버전, 이전 대화를 줄이는 compaction 설정도 함께 기록한다. 이 실행 조건 묶음을 식별하는 기록이 fingerprint다.

## 2. 패치를 남기는 것과 문제를 해결하는 것

에이전트가 문제를 해결하려면 작업한 내용을 패치로 남겨야 하고, 그 패치가 검증도 통과해야 한다. 두 실패는 점수만으로 구분되지 않는다. 과제 $N$개의 실제 해결 비율을 $S$라고 하자. 과제 $i$에서 작업 디렉터리의 변경을 잃지 않고 패치로 수집해 검증에 전달하는 사건을 $E_i$, 검증 결과를 $Y_i\in\{0,1\}$로 둔다. 여기서 1은 resolved, 0은 unresolved다. 패치를 전달하지 못하면 해결로 인정되지 않는다는 조건에서 기대 해결률은 다음과 같다.

$$
\mathbb{E}[S]=\frac{1}{N}\sum_{i=1}^{N}\Pr(E_i)\,\Pr(Y_i=1\mid E_i).
$$

앞의 확률은 **패치를 전달할 확률**, 뒤의 조건부 확률은 **전달한 패치가 문제를 해결할 확률**이다. 편집 명령이 실패했거나 변경을 수집하지 못했다면, 먼저 도구 실행과 수집 경로를 고쳐야 한다. 패치는 정상적으로 전달됐지만 검증에 실패했다면, 수정한 동작이 요구사항에 맞는지 조사해야 한다.

| 기록에 나타난 결과 | 다음에 확인할 것 | 점수에 영향을 주는 경로 |
|---|---|---|
| Agent error 또는 중단 | 실제 파일이 바뀌었는지, 그 diff가 수집됐는지 | 이미 만든 패치가 남을 수도 있으므로 오류 기록만으로 전달 실패를 판정할 수 없음 |
| 패치를 전달했지만 unresolved | 적용된 패치와 실패한 검증 테스트 | 전달된 수정안이 요구사항을 충족하지 못했거나 검증 환경에 문제가 있음 |
| 전체 12시간 초과 | 과제 준비와 에이전트 작업을 합친 전체 시간 | 개별 과제의 해결 여부와 별개로 제출 전체가 오류로 끝남 |
{: .quick-summary }

Agent error는 실행 중에 문제가 생겼다는 기록이지, 작업 결과를 모두 잃었다는 뜻은 아니다. 초기에 확인한 runtime은 예외가 발생하면 패치 수집 코드까지 도달하지 못할 수 있었다. 10월 23일 기준 v31 코드는 일반 실행 오류를 기록한 뒤에도 작업 디렉터리의 diff를 수집한다. 이 fallback 수집이 성공하고 패치가 테스트를 통과하면 agent error가 있어도 resolved가 된다. 따라서 timeout이나 context 오류가 발생한 실행도 수집한 패치와 verifier 결과를 각각 확인해야 한다.

초기에는 코드 수정의 질을 따지기 전에 해결해야 할 문제가 많았다. Kaggle의 L4 GPU 네 장에서 공개 과제 세 개를 돌린 첫 실행은 한 과제를 해결했다. 다른 한 과제에서는 같은 잘못된 호출이 55번 나온 뒤 context 오류가 났다. 나머지 한 과제에서는 분석을 맡은 보조 에이전트가 잘못된 셸 pipeline을 약 4분 동안 반복하다 노트북 전체의 제한 시간에 걸렸다. 두 실패 모두 유효한 소스 수정을 하기 전이었다. 이때는 더 나은 수정안을 요구하기에 앞서, 왜 도구 실행과 작업 흐름에서 막혔는지 살펴봐야 했다.

## 3. 도구 호출은 어디서 잘못됐나

모델이 “파일을 읽겠다”고 출력하는 것과 실제 파일 읽기 도구가 실행되는 것 사이에는 변환 단계가 있다. 서버의 **parser**가 모델 출력을 읽어 도구 이름과 인자로 바꾸고, harness가 그 인자로 도구를 호출한다. Gemma 4의 출력은 JSON이 아니라 문자열의 시작과 끝을 특수 토큰으로 표시하는 형식이다. 아래의 `<|"|>`가 그 구분 토큰이다.

```text
intended: read_file{filepath:<|"|>fastapi/openapi/utils.py<|"|>,start_line:400,end_line:568}
emitted:  read_file{filepath:<|"|>fastapi/openapi/utils.py\",start_line\":400<|"|>,end_line:568}
```

두 번째 줄은 원래 출력 토큰이 남아 있지 않아 기록된 인자로 복원한 것이다. Parser는 문자열을 시작한 뒤 다음 구분 토큰을 만날 때까지 읽는다. 모델이 파일 경로 끝에 일반 따옴표나 escape된 따옴표, backtick을 쓰면 parser는 이를 끝으로 인식하지 못한다. 그 결과 뒤의 `",start_line":400`까지 파일 경로에 들어간다. 도구는 전달받은 이름의 파일을 찾지 못해 오류를 낸다. 따라서 “파일이 없다”는 응답을 받고 다른 경로만 찾으면, 문자열을 잘못 닫은 원인은 그대로 남는다.

Thinking을 끈 번들로 과제 22개를 실행한 비교에서는 이런 잘못된 호출이 223번, 인자가 빠졌다는 이유로 거부된 호출이 80번 있었다. `edit_file`에서도 `new_string`을 backtick으로 닫으면 parser가 뒤의 `old_string`까지 앞 문자열로 읽을 수 있다. 모델이 수정할 코드를 생각했더라도, 도구가 받은 요청에는 필요한 인자가 없는 것이다.

## 4. 한 번 시작된 반복은 오래 이어졌다

잘못된 호출을 한 번 보낸 뒤 고쳐서 다시 요청한다면 다음 작업을 이어 갈 수 있다. 문제는 오류를 받고도 같은 호출을 계속 보냈다는 점이다. 반복을 분석할 때는 다음 세 단위를 구분했다.

| 단위 | 이 분석에서 센 것 |
|---|---|
| 같은 호출 | 도구 이름과 parser가 만든 인자 값이 모두 같은 호출. 인자 key의 순서만 다른 경우는 같게 처리 |
| Streak 길이 $k$ | 같은 호출이 중간에 다른 호출 없이 이어진 횟수. 인자 값이 달라지면 새 streak가 시작됨 |
| 연속 호출 쌍 | 바로 이웃한 두 호출. 앞 호출까지의 streak 길이를 보고 뒤 호출이 같은지 비교 |
{: .quick-summary }

파일 이름이 같아도 읽는 줄 번호가 바뀌면 다른 호출이다. $k=1$은 어떤 호출이 한 번 나온 시점이고, 다음 호출도 같으면 길이 2인 반복에 진입한다. 이미 같은 호출이 세 번 나왔다면 $k=3$이다. 각 시점에서 다음 호출까지 같을 확률을 아래처럼 정의한다.

$$
h(k) = \Pr(\text{next call identical} \mid \text{current streak } k).
$$

따라서 $h(1)$은 한 번 보낸 호출을 다시 보낼 확률이고, $h(3)$은 이미 세 번 연속해서 보낸 호출을 네 번째에도 보낼 확률이다. 반복 중인지와 무관하게 매번 확률 $q$로 반복하는 memoryless 모형에서는 모든 $k$에 대해 $h(k)=q$다. Thinking 없이 실행한 과제 22개의 trace, 도구 호출 1,404개는 이 모형과 달랐다. Trace는 모델의 요청과 도구 응답, 편집 등을 시간순으로 남긴 실행 기록이다.

$h(1)=0.056$은 호출이 한 번 나온 시점에서 다음에도 같은 호출이 나올 비율이다. 같은 호출이 이미 세 번 이상 이어진 구간만 모으면 다음에도 반복한 비율은 $643/663=0.97$이고, 개별 구간의 $h(k)$도 0.96–1.00이었다. 반복을 처음 시작하는 경우는 적었지만, 긴 반복에 들어간 뒤에는 같은 호출을 또 보내는 경우가 대부분이었다.

전체 연속 호출 쌍을 합친 평균 반복률은 $\hat q=0.512$다. 모든 시점에서 이 확률로 반복한다고 가정하면, 실제 실행 길이들을 가진 22개 실행에서 같은 호출이 20번 이상 이어지는 실행의 기대 개수는 $1.5\times10^{-3}$이다. 실제로는 **11개**였다. 평균 반복률만 맞춘 모형은 이렇게 긴 반복을 재현하지 못한다. 반복을 시작하는 경우와 이미 반복 중인 경우를 나눠 보기 위해 다음 두 확률을 쓴다.

- **진입 확률** $\alpha=h(1)$
- **지속 확률** $\beta\approx h(k)$, $k\ge3$

일단 반복 중일 때 다음에도 반복할 확률을 매번 $\beta$라고 가정하면, 추가 반복 횟수의 기대값은 $\beta/(1-\beta)$다. $\beta=0.97$이면 약 32번이다. 이 계산은 반복이 얼마나 많은 호출을 차지할 수 있는지 설명한다. 다만 실제 반복 원인을 두 상태로 나눠 밝혀낸 것은 아니다. 과제별 반복 성향이 다를 수 있고, 긴 streak를 관찰하는 시점에는 이미 오래 반복한 실행만 남아 있다. 시간이나 호출 한도에 걸리면 그 뒤의 행동은 관찰하지 못한다. 이런 차이도 여러 실행을 합친 곡선에 영향을 준다.

가능한 설명 중 하나는 모델이 context에 쌓인 앞선 호출을 그대로 따라 한다는 것이다. 조사한 반복 구간에서는 이전의 같은 호출과 바뀌지 않은 도구 결과가 대화 기록에 남았고, 그 사이에 reasoning text가 없었다. 이런 입력이 반복을 강화했을 가능성은 있지만, 곡선만으로 원인을 확정할 수는 없다.

**반복할 때마다 다음 요청의 prompt도 길어진다.** 모델은 이전 호출과 도구 응답을 입력으로 받아 다음 호출을 정한다. 같은 오류가 반복돼도 그 기록은 계속 추가된다. 이 입력 전체를 context라고 하며, 서버는 prompt와 요청한 최대 출력 길이의 합이 아래 한도 안에 들어와야 요청을 받아들인다.

$$
C_{\mathrm{prompt}} + M_{\mathrm{requested}} \le 32{,}768,
$$

$C_{\mathrm{prompt}}$는 다음 요청에 들어가는 prompt의 토큰 수다. $M_{\mathrm{requested}}$는 실제로 생성할 응답 길이가 아니라, 요청에서 허용한 최대 출력 토큰 수다. 응답이 짧게 나올 예정이어도 서버는 요청을 받을 때 그 최대값으로 한도를 검사한다. 첫 요청은 이 한도 안에 들어온다고 가정하고, 그 prompt 길이를 $C_0$라고 하자. Compaction으로 이전 대화를 줄이지 않고, 호출이 끝날 때마다 다음 prompt가 일정하게 $c$토큰씩 늘어난다면($c>0$) 첫 호출을 포함한 총 허용 호출 수는 다음과 같다.

$$
n_{\max} = 1 + \left\lfloor \frac{32{,}768 - M_{\mathrm{requested}} - C_0}{c} \right\rfloor.
$$

첫 진단 실행에서는 $M_{\mathrm{requested}}=8{,}192$, $C_0=18{,}033$, $c=119$였다. 내림 연산으로 얻는 값은 54다. 첫 호출 뒤에 54번을 더 할 수 있으므로 $n_{\max}=55$다. 실제로 같은 호출이 55번 나온 뒤, 프롬프트가 24,578토큰이 된 56번째 요청이 거부됐다. 나중에 $M_{\mathrm{requested}}=4{,}096$으로 실행했을 때도 거부된 요청의 프롬프트는 28,673토큰이었다. 허용치 28,672보다 정확히 하나 많았다.

$\beta=0.97$인 가상의 반복 과정이 앞으로도 55번 계속 이어질 확률은 $0.97^{55}\approx0.19$다. 이것을 실제 과제의 실패 확률로 읽어서는 안 된다. 다만 반복이 무한히 이어지지 않더라도, 제한된 context를 모두 써 버릴 만큼 길어질 수는 있음을 보여 준다.

해결한 과제는 5개에서 7개로 늘었다. 두 번들 중 한쪽만 해결한 과제는 둘이고, 둘 다 thinking을 켠 쪽이 이겼다. 이 두 과제만으로 성능 개선을 확신하기는 어렵다. 두 번들이 이길 가능성이 같다는 가정에서 이만큼 또는 더 한쪽으로 치우친 승패가 나올 확률을 구하면, 정확한 양측 검정의 $p=0.5$다. 반면 반복 호출과 패치 수집에서는 다음 차이가 나타났다.

<p class="table-caption"><span class="table-label">표 2.</span> 같은 공개 과제 22개에서 비교한 반복 호출과 패치 수집 결과.</p>

| 지표 | Thinking off | Reasoning 512 |
|---|---:|---:|
| 진입 확률 $\alpha=h(1)$ | 0.056 | 0.018 |
| 지속 확률 $\beta$ ($k\ge2$ 구간 합산) | 0.95 | 0.47 |
| 같은 호출이 두 번 이어진 뒤 추가 반복 횟수의 기대값 $\beta/(1-\beta)$ | 21 | 0.9 |
| 같은 호출이 20번 이상 이어진 실행 | 11 | 0 |
| 패치를 수집한 실행 | 9 | 15 |

thinking을 켠 쪽에서는 $k=1$ 이후에 관측한 호출 쌍이 17개뿐이어서, 지속 확률은 $k\ge2$를 합쳐 계산했다. 켠 쪽은 $\beta=8/17$, 끈 쪽은 $669/701$이다. 이 비교에서 진입 확률은 약 3분의 1로 낮아졌고 지속 확률도 크게 낮아졌다. 표의 기대 반복 횟수는 반복에 진입한 뒤에도 같은 확률로 반복한다고 가정한 4절의 계산을 적용했다. 같은 실행 안의 호출 쌍을 여러 번 센 결과이므로, 서로 독립인 과제 표본처럼 다룰 수는 없다.

Thinking에 쓴 시간도 세션 제한에 포함된다. 로컬 장비에서 모델 요청 한 번에 걸린 시간은 켰을 때 7.2초, 껐을 때 3.3초였다. 모델 요청은 다음 응답을 생성해 달라는 요청이고, 도구 호출은 그 응답에 따라 파일을 읽거나 명령을 실행하는 작업이다. 모델 요청마다 도구 호출이 하나씩 나온다고 보장되지는 않는다. 세션 길이를 $T_{\mathrm{session}}$, 모델 요청 한 번의 시간을 $t_{\mathrm{request}}$라고 하면, 모델 요청 수 $K_{\mathrm{calls}}$를 다음처럼 대략 계산할 수 있다.

$$
K_{\mathrm{calls}} \approx \frac{T_{\mathrm{session}}}{t_{\mathrm{request}}},
$$

모델 요청 시간만 보면 같은 세션에서 할 수 있는 요청이 거의 절반으로 줄어든다. 실제로는 도구 실행 시간도 필요하다. 그렇다면 줄어든 호출이 모두 문제 해결에 필요했던 호출인지 살펴볼 필요가 있다.

thinking을 끈 trace에서는 연속 호출 쌍 1,382개 중 707개가 반복이었다. 켠 쪽은 575개 중 18개였다. 각 실행의 첫 호출을 포함하고 직전 호출과 같은 것을 빼면 **697개 대 579개**가 남는다. 전체 호출은 57% 줄었지만 연속 중복을 제외한 호출은 약 17%만 줄었다. 중복이 없다고 반드시 유용한 호출은 아니다. 그래도 전체 호출 수만 볼 때와 달리, 줄어든 호출 중 상당수가 반복이었다는 사실을 알 수 있다.

그렇다고 thinking을 무작정 늘려도 되는 것은 아니었다. 사실상 길이를 제한하지 않은 변형은 5분 세션에서 22개 중 15개 과제가 시간 초과로 끝났고 호스트 점수는 0.05였다. 길이를 제한한 버전은 0.12를 두 번 받았으며, 같은 epoch에서 수정하지 않은 recovery 번들은 0.06을 받았다. 초기 recovery 계열에서 로컬과 호스트의 우열이 일치했던 사례다. 현재 E0052의 설정이나 이후 runtime에서의 최적값을 정한 실험은 아니다.

## 6. 로컬 평가도 먼저 검증해야 한다

에이전트가 과제에 맞는 파일을 받아 읽고 고쳤는지, 평가기가 그 수정본을 검사했는지부터 확인해야 로컬 해결률을 비교할 수 있다. 초기에는 에이전트의 능력처럼 보였던 결과가 실행 경로나 평가 도구의 오류로 밝혀진 경우도 있었다.

<p class="table-caption"><span class="table-label">표 3.</span> 에이전트의 특성처럼 보였지만 benchmark나 verifier를 확인하다 찾은 문제.</p>

| 과제 목록이 비었는데도 실행이 성공했다고 나왔다. | 0개 중 0개를 처리한 실행을 완료로 계산했다. |

과제마다 수정 전 저장소가 검증에 실패하고 reference patch를 적용하면 통과하는지 확인한다. Reference patch는 과제에 제공된 기준 수정안이다. 이 두 대조군으로 환경 준비와 채점의 중요한 오류를 찾을 수 있지만, 필수 테스트 이름을 잘못 매칭하는 오류는 놓칠 수 있다. 예를 들어 이름이 비슷한 테스트만 있는 보고서로도 통과하는지를 별도로 검사해야 한다. 이런 오류를 잡기 위해 일부러 실패해야 하는 입력을 넣는 것이 negative control이다. GPU 실행 묶음에 앞서서는 정해진 응답을 내는 가짜 모델을 연결해, 도구 실행부터 최종 채점까지 한 과제는 해결, 다른 과제는 미해결로 나오는지도 확인한다.

에이전트가 만든 패치를 고정하고 테스트만 다시 실행하면, 에이전트의 새 행동 없이 채점 경로를 비교할 수 있다. 이 재실행을 replay라고 부른다. 원래의 subprocess 경로는 호스트의 자식 프로세스로 명령을 실행하고, 비교 경로인 Docker는 컨테이너에서 검증한다. v28의 한 로컬 조건에서는 **검증을 마친 replay 137건**이 모두 원래 subprocess 판정과 같았다. 실행했으나 검증을 마치지 못한 replay 28건은 별도로 남겼다.

이 일치를 모든 runtime에 적용할 수는 없었다. v29에서 변경된 패치를 후속 조사했을 때는 계획한 35건 중 34건을 실행했고, 28건은 검증을 마쳤다. 이 28건 중 두 이슈에 해당하는 6번의 시도는 원래 판정과 달랐다. 보호 대상 테스트·설정 변경을 걸러 내는 동작은 이 차이와 부합했다. 다만 이 조사에서 전체 과제를 다시 채점한 것은 아니다. **어느 조건에서 일치했는지를 기록해야**, 그 조건이 바뀐 뒤에도 과거의 검증 결과를 그대로 믿는 일을 피할 수 있다.

현재 verifier에서 재현한 테스트 이름 매칭 문제와, subprocess에서 발견한 경로 치환 문제는 적용 범위도 다르다. 후자는 셸 문자열 안에 적은 작업 경로까지 로컬 backend가 바꿔 버리는 동작이다. 이 때문에 셸로 파일 내용을 쓸 때 의도와 다른 경로가 들어갈 수 있다. 이 동작을 비공개 Docker sandbox에서도 확인한 것은 아니다. 재현 기록에 runtime과 backend를 함께 남겨야, 어느 결과를 다시 점검해야 하는지 알 수 있다.

로컬 sandbox는 에이전트와 평가기를 같은 사용자로 실행한다. 따라서 파일 읽기 도구가 막더라도 셸 명령으로 reference 자료를 읽을 가능성이 있다. 점검한 trace에서는 그런 기록을 찾지 못했지만, trace는 도구 요청과 응답을 남기는 이벤트 로그다. Python 코드 안에서 간접적으로 어떤 파일을 열었는지까지 모두 감시한 기록은 아니다. 사용 자료를 기록하는 것과 파일 접근을 실제로 차단하는 것은 별도로 해결해야 한다.

같은 과제를 반복해서 보며 프롬프트를 고르면, 가중치를 학습하지 않아도 그 과제에 맞는 설정을 고르게 된다. 이 영향을 줄이기 위해 공개 과제 25개는 기록된 모델 실행에서 제외하고, 나머지 과제는 설계·분석·학습 중 어디에 썼는지 관리한다. 이 holdout은 개발 과정에서 보지 않은 과제로 비교하기 위한 것이다. 모델의 사전 학습에 포함됐는지나 모든 간접 파일 접근까지 보장하는 조치는 아니다.

## 7. 호스트 점수로 어디까지 알 수 있을까

호스트는 비공개 과제별 결과 대신 합산 점수를 돌려준다. 따라서 숫자가 달라졌을 때 먼저 어떤 차이를 말하는지 구분해야 한다.

| 질문 | 비교하는 대상 | 필요한 해석 |
|---|---|---|
| 표시 점수는 몇 과제에 해당하는가? | 해결 수와 리더보드에 표시된 소수 | 과제 수와 소수점 처리 규칙이 필요함 |
| 같은 패키지를 다시 실행하면 왜 달라지는가? | 같은 과제 집합에서 나온 여러 제출 결과 | 실행 변동과 관찰하지 못한 서버 조건을 구분해야 함 |
| Public 결과가 Private에서도 유지되는가? | 서로 다른 과제 집합의 해결률 | 과제 구성과 과제 사이의 의존성에 대한 가정이 필요함 |
{: .quick-summary }

리더보드에서 관찰한 점수들은 Public 과제가 58개라고 가정한 다음 식과 맞는다. $k$는 해결한 Public 과제 수이며, 식은 해결률의 소수점 둘째 자리 아래를 버려 표시한다.

$$
\mathrm{displayed}(k) = \frac{\lfloor 100k/58 \rfloor}{100}, \qquad k = 0, 1, \ldots, 14.
$$

이 식에서는 6개 해결이 0.10, 9개가 0.15, 11개가 0.18, 14개가 0.24에 해당한다. 주최 측은 Public 과제가 약 60개라고 안내했다. 대회 metadata에서는 소수점 둘째 자리 아래를 버려 표시한다는 것을 확인했지만, 정확한 Public 과제 수는 공개하지 않았다. 58개라는 해석은 스냅샷과 일치할 뿐 실제 과제 목록으로 확인한 값은 아니다. 아래의 과제 수 환산도 이 해석을 전제로 한다.

**같은 조건으로 분류한 두 제출에서도 점수는 달랐다.** 기준 번들에서 예산 안내만 지운 변형 E0053의 동일한 ZIP이, HE-11에 배정된 두 제출에서 0.10과 0.15를 받았다. 파일은 바이트 단위로 같았고 관찰한 공개 호스트 fingerprint도 같았다. 하지만 비공개 과제별 결과, 서빙 로그, 실제 배포 기록은 없다. 따라서 차이가 무작위 실행 변동 때문이라고 단정할 수는 없다. 이 두 제출에서 같은 파일이 같은 합산 점수를 내지 않았다는 사실까지는 확인했다.

같은 패키지를 같은 과제에서 다시 실행할 때 과제 $i$를 해결할 확률을 $\pi_i$라고 하자. 각 과제의 성공 여부 $Y_i$를 더한 $K_{\mathrm{solves}}=\sum_iY_i$가 해결한 과제 수다. 그 수가 실행마다 얼마나 달라지는지를 나타내는 분산은 다음과 같다.

$$
\operatorname{Var}(K_{\mathrm{solves}})=\sum_i\pi_i(1-\pi_i)+2\sum_{i<j}\operatorname{Cov}(Y_i,Y_j).
$$

첫 항은 각 과제 자체의 성공·실패 변동이고, 공분산 항은 과제들이 함께 잘 풀리거나 함께 실패하는 영향을 더한다. 예를 들어 서버가 느리거나 앞 과제에서 시간을 많이 썼다면 여러 과제의 결과가 함께 달라질 수 있다. 과제 결과가 서로 독립이라면 공분산 항은 0이지만, 여기서는 그런 독립성을 확인하지 못했다. 합산 점수 두 개로는 각 $\pi_i$나 공분산, 일반적으로 쓸 만한 표준편차를 알아낼 수 없다. 특히 이 차이를 **호스트에 과제 두 개 정도의 노이즈가 있다는 측정 결과로 읽어서는 안 된다.**

**변동이 어느 정도라면 비교가 얼마나 어려워질까?** 두 번들의 실행 결과가 서로 독립이고, 같은 표준편차 $\sigma$를 가지며 그 값을 안다고 가정하자. 오차를 정규분포로 근사할 수 있다면, 기대 해결 수가 $\Delta$만큼 다른 두 번들을 한 번씩 실행해 우열을 올바르게 판단할 확률은 다음과 같다.

$$
\Pr(\text{correct order})\approx\Phi\!\left(\frac{\Delta}{\sigma\sqrt{2}}\right).
$$

<p class="table-caption"><span class="table-label">표 5.</span> 변동 폭을 가정했을 때 두 번들의 우열을 올바르게 판단할 확률.</p>

| 가정한 기대 해결 수의 차이 $\Delta$ | $\sigma=1$일 때 | $\sigma=1.5$일 때 | $\sigma=2$일 때 |
|---|---:|---:|---:|
| 과제 1개 | 0.76 | 0.68 | 0.64 |
| 과제 2개 | 0.92 | 0.83 | 0.76 |
| 과제 3개 | 0.98 | 0.92 | 0.86 |

여기서 $\Phi$는 표준정규분포의 CDF, 즉 주어진 값보다 작은 결과가 나올 확률을 구하는 함수다. 표의 $\sigma$는 해결 과제 수의 표준편차로, 우리 제출에서 추정한 값이 아니라 계산을 위해 가정한 값이다. 변동 폭이 클수록 같은 기대 성능 차이를 점수 한 번으로 구분하기 어려워진다. 반대로 점수 차이가 뚜렷하지 않다고 두 번들의 성능이 같다고 결론 내릴 수도 없다.

**Public과 Private의 차이는 다른 문제다.** 같은 Public 과제에서 실행 결과가 달라지는 것과, 아예 다른 과제로 평가받는 것은 구분해야 한다. 과제를 독립적으로 뽑고 해결률이 $p$, Public이 58개, Private이 60개라고 가정하면 두 해결률 차이의 표준편차는 다음과 같다.

$$
\operatorname{SD}(\hat p_{\mathrm{Public}}-\hat p_{\mathrm{Private}})
\approx\sqrt{p(1-p)\left(\frac{1}{58}+\frac{1}{60}\right)}\approx0.072
\quad (p=0.19).
$$

이는 서로 다른 과제 표본에서 생기는 차이를 계산한 것이다. 같은 과제에 여러 번 제출했을 때의 변동을 계산한 값이 아니다. 실제 split 구성 방식과 과제 간 의존성을 모르므로, 0.072를 이 대회의 변동 예측이나 신뢰구간으로 사용할 수는 없다.

## 8. 같은 과제로 비교해도 주의할 점이 있다

로컬에서는 두 번들에 같은 과제를 주고 seed를 기록하며 실행 순서를 번갈아 가며 비교한다. 이렇게 조건을 맞추면 어느 과제에서 결과가 달라졌는지 볼 수 있다. 다만 같은 과제를 seed 두 개로 실행한다고 독립된 과제가 두 개 생기는 것은 아니다.

기준과 변형이 모두 성공하거나 모두 실패한 쌍은 승패 차이가 0이다. 부호검정은 한쪽만 해결한 쌍, 즉 **discordant pair**에서 어느 쪽이 더 많이 이겼는지 본다. 두 번들이 이길 가능성이 같다는 가정에서는 각 승패를 공정한 동전 던지기처럼 계산한다. **각 쌍이 서로 독립이고**, 결과가 갈린 쌍이 $d$개, 그중 후보가 이긴 쌍이 $g$개일 때 지금만큼 또는 더 한쪽으로 치우친 승패가 나올 확률은 다음과 같다.

$$
p=\min\!\left(1,\;2\sum_{j=\max(g,\,d-g)}^{d}\binom{d}{j}2^{-d}\right).
$$

2승 0패면 $p=0.5$, 6승 1패면 $p=0.125$다. 이 값은 후보가 개선됐을 확률이 아니다. 동률이라는 가정 아래 이런 승패가 나올 가능성을 계산한 것이다. 같은 이슈에서 seed만 바꾼 승리가 여러 번 들어갔다면 쌍들이 독립이라고 보기 어려워 과제 단위 검정으로 곧바로 사용할 수 없다. 아래 표는 해결한 **시도 수**를 보고하고, 과제별 차이는 따로 살핀다.

현재 기준 번들은 도구 호출 28번, 세션당 8분, thinking 4,096토큰을 허용하며 프롬프트에 짧은 예산 안내가 들어 있다. 같은 파일로 0.15, 0.15, 0.15, 0.17, 0.18을 받았지만 여러 호스트 epoch에 걸친 결과다. 어느 epoch인지 모호한 구간도 포함된다. **이 가운데 명확한 HE-11 기준 제출은 한 번뿐이다.** 같은 환경에서 다섯 번 반복한 결과로 볼 수 없다.

표의 각 행은 별도의 비교다. 같은 기준 패키지를 썼더라도 기준 실행 자체와 runtime 조건이 모두 같았던 것은 아니다. 40개 과제의 결과도 잠정 관찰로만 보고하며 확증 실험을 마친 결과로 사용하지 않는다. 중단하거나 다음 단계로 넘어갈 규칙을 실행 전에 정한 경우도 있지만, 예산 안내 변형의 판단 기준은 이미 세 실행 묶음의 결과를 본 뒤 제안했다. 관찰한 결과에 맞춰 만든 판단 기준을 사전 등록한 검정처럼 소개할 수는 없다.

10월 17일까지 후보 설계 7개에 쓴 pod 시간을 합치면 약 51시간이었다. 이 범위에서는 기준 번들을 대체할 후보를 고르지 못했다. 여기에는 paired comparison뿐 아니라 가능성을 살핀 초기 선별과 작은 canary 실행도 들어 있다. Canary는 더 큰 실험에 앞서 변경이 의도한 방식으로 동작하는지 좁은 범위에서 확인하는 실행이다. 따라서 51시간은 그때까지의 투자 규모이지, 동일 조건에서 후보 일곱 개를 검정한 비용이나 이후까지 포함한 누적 비용은 아니다.

**로컬의 개선은 호스트에서도 유지됐을까?** 기준 번들은 기록된 공개 패널에서 시도의 약 36%를 해결했다. 외부 과제의 원래 두 seed 비교에서는 Pallets 계열 저장소 6곳에서 고른 과제 40개를 80번 시도해 31번, 즉 38.75%를 해결했다. 이 외부 과제 40개를 X40 패널이라고 부른다. 명확한 HE-11 호스트 기준 결과는 0.18이다. Public 과제가 58개라는 해석을 적용하면 11/58, 약 19%다.

두 해결률의 비율로 다음 프롬프트 변경의 효과를 환산할 수는 없다. 로컬과 호스트는 과제 구성, 개발 중 얼마나 자주 보았는지, 장비와 실행 절차가 모두 다르다. 주최 측은 강한 모델이 풀 수 있는지 확인해 비공개 과제를 골랐다고 했지, 그 모델에게 어렵도록 골랐다고 하지는 않았다. 이 차이들이 해결률에 각각 얼마나 영향을 줬는지는 분리해서 측정하지 못했다.

예산 안내를 지운 변형에서도 이 한계가 드러난다. 한 비교에서는 22/44를 해결했지만 나중의 로컬 실행에서는 13/44였다. **runtime과 seed가 모두 바뀌었고**, 뒤의 실행에는 조건을 맞춘 E0052 대조군도 없었다. 이 차이만으로 runtime이 성능을 떨어뜨렸다고 말할 수는 없다. 호스트 점수 0.10과 0.15도 이 변형이 더 낫거나 같다는 것을 입증하지 못한다. 현재로서는 로컬에서 본 개선이 호스트에서도 유지된다고 확인하지 못했으므로 수정하지 않은 기준 번들을 계속 사용한다.

## 9. 12시간 제한에서는 해결률과 완주 가능성을 함께 봐야 한다

앞의 비교에는 해결 수 외에 고려해야 할 실패가 하나 더 있다. 개별 과제를 몇 개 더 해결하더라도 전체 실행이 시간 안에 끝나지 않으면 점수를 받지 못한다.

전체 시간에는 모델이 답하는 시간 외에도 서버 시작과 과제별 환경 준비가 들어간다. Public과 Private을 합친 전체 과제 수를 $N_{\mathrm{all}}$이라고 하면 $T=h+\sum_{i=1}^{N_{\mathrm{all}}}(s_i+a_i)$다. $h$는 공통 부대 시간, $s_i$는 과제 준비와 한도에 포함되는 기타 부대 시간, $a_i$는 그 과제의 에이전트 작업 시간이다. 12시간을 넘기면 끝낸 과제만 채점하는 대신 제출 전체가 오류로 끝난다.

시간을 더 써서 해결률을 높이더라도, 전체 실행을 마치지 못하면 그 개선으로 점수를 받을 수 없다. 이 관계를 계산하려고 Public의 실제 해결 비율 $S_{\mathrm{Public}}$과 계획용 지표 $U$를 구분한다.

| 지표 | 계산 범위 | 뜻 |
|---|---|---|
| 전체 시간 $T$ | Public과 Private을 합친 모든 과제 | 공통 시작 시간, 과제 준비, 에이전트 작업 시간을 더한 값 |
| 실제 Public 해결률 $S_{\mathrm{Public}}$ | Public 과제 | 표시 점수로 바꾸기 전의 해결 수 / 과제 수 |
| 계획용 지표 $U$ | 제출 전체의 완주 여부와 Public 해결률 | 전체 실행을 마치면 실제 Public 해결률, 시간 초과로 실패하면 0 |
{: .quick-summary }

$U$에서 시간 초과를 0으로 계산하는 것은 계획을 위한 정의다. Kaggle이 오류 난 제출에 0점을 준다는 뜻은 아니다. 전체 실행을 마칠 확률과, 마쳤을 때의 Public 해결률을 곱하면 $U$의 기대값이 된다.

$$
\mathbb{E}[U]=\Pr(T\le H)\,\mathbb{E}[S_{\mathrm{Public}}\mid T\le H],
\qquad H=720\text{ minutes}.
$$

과제별 총시간 $s_i+a_i$가 서로 독립이고 같은 평균 $\mu$, 표준편차 $\sigma$를 가진다고 가정하자. 여기서 두 값의 단위는 시간이다. 전체 과제 시간의 평균과 변동 폭을 정규분포로 근사하면, 전체 시간이 한도 $H$ 안에 들 확률을 다음처럼 계산할 수 있다.

$$
\Pr(T\le H)\approx\Phi\!\left(\frac{H-h-N_{\mathrm{all}}\mu}{\sigma\sqrt{N_{\mathrm{all}}}}\right).
$$

실험 기록에는 주의할 만한 사례가 있다. 이전 thought를 지운 변형은 로컬에서 기준과 같은 17/44를 해결했지만, 측정한 **에이전트 세션 시간**은 약 18% 늘었다. 이후 호스트 실행은 시간 초과로 끝났다. 시간 초과 위험을 의심할 만한 사례지만, 로컬의 세션 시간 증가가 호스트 시간 초과의 원인이었다고 확인한 것은 아니다. TP1 Ada에서 얻은 세션 시간 비율을 TP4 호스트의 모든 과제 시간에 그대로 적용할 수 없고, 환경 준비 시간을 측정한 것도 아니다. 특히 1.05배나 1.10배 미만이면 안전하다는 기준을 검증한 적은 없다.

기준 번들의 8분 상한도 완주를 보장하지 않는다. 환경 준비를 빼고도 $120\times8=960$분까지 가능하다. 성공한 제출이 있었다는 것은 모든 과제에서 상한을 다 쓰지는 않았다는 뜻이다. 실제로 시간이 얼마나 남았는지는 여전히 모른다.

## 10. 에이전트가 스스로 검사해도 남는 문제

thinking과 새로운 도구 오류 처리 덕분에 초기 실패 중 일부는 줄었다. 그다음에는 패치를 만들고도 문제를 해결하지 못하는 경우를 살펴봤다. 외부 과제 40개에서 기준 번들을 140번 시도했을 때, 오류가 다섯 호출 이상 이어진 경우는 5번이었고 모두 미해결이었다. 이 140번에는 서로 다른 세 실험 묶음의 결과와 정식 최종 비교로 인정한 범위 밖의 시도가 포함돼 있다. 새로운 평가 표본으로 볼 수는 없다.

에이전트가 확인한 동작을 $C$, 평가기의 테스트가 요구하는 동작을 $R$이라고 하자. 에이전트가 프로그램이 끝까지 실행되는지만 확인했다면, 결과값까지 맞는지는 알 수 없다. 자체 검사 하나로 모든 비공개 assertion을 보장할 필요는 없지만, 적어도 이슈의 요구사항과 관련된 동작을 최종 코드에서 확인해야 한다.

**검증에 실패한 시도 69번 중 52번**은 reference fix가 고친 파일을 하나 이상 수정했다. 과제로는 19개였다. 이는 코드를 편집하고도 실패한 사례를 찾는 기준은 되지만, 원인 위치를 정확히 찾았다는 증거는 아니다. 같은 파일의 엉뚱한 곳을 고쳤을 수 있고, 다른 파일에서 해결할 수도 있다. 그중 33번에서는 수정 뒤 Python·pytest 계열 명령의 도구 응답이 오류가 아닌 것으로 분류됐다. 하지만 그 명령이 관련 assertion을 실행했는지, 종료 코드가 무엇인지, 마지막 수정까지 검사했는지는 확인되지 않았다. 이 수만으로 “자체 테스트는 통과하고 비공개 테스트만 실패했다”고 분류할 수는 없다.

Rich에서 너비가 0인 문자를 다룬 사례는 두 검사의 차이를 직접 보여 준다. 에이전트는 함수가 종료하는지 확인했고, 평가기는 단독 variation selector를 입력했을 때 정확한 span 값이 나오는지 검사했다. 종료하는 것과 올바른 범위를 반환하는 것은 서로 다른 요구사항이다. 저장소의 기존 테스트에는 관련 출력 형식이 있었지만 찾아본 trace에는 그 부분을 읽은 기록이 없었다. 활용할 수 있었을 정보가 있었던 셈이다. 이를 읽었으면 해결했을지는 별도로 확인하지 못했다.

문제 설명이 얼마나 자세한지도 살펴봤다. 공개 과제 22개를 네 번 실행한 결과, 설명이 120자 이하인 과제는 32번 중 7번, 더 긴 과제는 56번 중 24번 해결했다. 이를 odds ratio로 정리하면 다음과 같다.

$$
\mathrm{OR}=\frac{7/25}{24/32}\approx0.37.
$$

여기서 $7/25$와 $24/32$는 각각 해결한 시도 수를 실패한 시도 수로 나눈 odds다. 두 해결률을 직접 나눈 값이 아니다. 서로 다른 과제는 설명이 짧은 8개와 더 긴 14개이며, 나머지는 같은 과제를 반복한 시도다. 88개의 독립된 과제를 비교한 것이 아니고, 이 22개 과제끼리의 독립성까지 확인한 것도 아니다. 설명 길이는 모델이 얻을 수 있는 정보량의 간접 지표에 가깝고, 저장소와 변경 유형도 함께 다르다. 따라서 설명 길이의 인과적 효과나 $p$값을 주장하지 않는다.

이슈에 더 맞는 검사를 하도록 프롬프트도 바꿔 봤다. 수정 전에 실패하는 검사를 정하고 수정 뒤 같은 검사를 다시 실행하게 했지만, 이 절차를 적용할 수 있었던 8번 중 끝까지 수행한 것은 1번이었다. 이슈에서 관련 정보를 뽑는 helper도 16번 중 7번은 사용하지 않았다. 앞선 일부 trace에서는 긴 절차보다 짧은 명령 예시를 더 잘 따라 했다. 그러나 명령을 따라 하는 것과 올바른 검사를 골라 해결률을 높이는 것은 별개다.

추가 지시를 만들려면, 에이전트가 어떤 정보를 보고도 잘못 판단했는지부터 찾아야 한다. 실패한 검사의 메시지를 받고도 통과했다고 진행한 경우라면 그 메시지를 다시 확인하게 할 수 있다. 이런 식으로 모델이 볼 수 있었던 단서를 선정한 8개 사례에서 찾았지만, 짧은 지시 하나로 바로잡을 만큼 분명한 모순은 찾지 못했다. 6개 사례에서는 평가기가 요구한 세부 사항이 문제 설명에 없었다. 저장소의 다른 맥락에서 알아낼 수 있었을 가능성과 약한 아이디어 두 개는 남았다.

따라서 이슈의 시나리오에 맞는 검사를 추가하자는 변경안은 보류했다. Reference 파일과 겹친 실패가 52번이라는 집계는 조사할 대상을 좁혀 줄 뿐, 어떤 지시로 고칠 수 있는 실패가 52번이라는 뜻은 아니기 때문이다.

## 11. adapter와 작은 모델: 실행 준비와 성능 검증은 별개다

프롬프트를 바꾸는 대신 LoRA adapter로 모델의 행동을 학습시킬 수도 있다. Adapter는 base model에 추가하는 학습 가중치다. 이 경로를 선택하려면 학습 데이터를 만들 수 있는지, 서버가 adapter를 실제로 적용하는지, 시간 안에 실행되는지, 수정 성능이 좋아지는지를 각각 확인해야 한다.

주최 측은 9월 27일 LoRA 문제를 수정했다고 알렸고, 이후 rank 64 이하 adapter로 점수가 나온 사례도 있다고 밝혔다. 해당 환경에서 실행 가능한 경로가 있다는 근거다. 모든 adapter가 자원에 맞거나 코드 수정 성능을 높인다는 보장은 아니다. 다른 참가자들은 서빙 비용이 늘고 KV cache의 가용 용량이 줄었다고 보고했다. KV cache는 앞선 토큰의 attention 계산에 쓰는 정보를 보관하는 메모리다. 참고할 만한 보고지만, 우리 패키지에서 측정한 값은 아니다.

Trajectory는 한 과제를 시작해서 끝낼 때까지의 모델 요청·응답과 도구 실행 기록이다. 10월 22일에는 **공개 과제 37개에서 해결에 성공한 기준 번들의 trajectory 65개**로 학습 데이터 **S1**을 만들었다. 한 trajectory에는 모델 요청이 여러 번 들어 있다. 각 요청에서 모델이 받은 prompt와 생성한 response를 한 sample로 묶으니 **호출별 sample 1,239개**가 나왔다.

이 sample들에는 **target token 259,576개, forward token 10,938,513개**가 있다. Target token은 모델이 생성하도록 학습할 출력이고, forward token은 그 출력을 예측할 때 함께 처리할 입력까지 센 수다. 예를 들어 prompt에 이슈·코드·이전 도구 응답이 있고 response가 `edit_file` 호출이라면, 입력과 호출 출력은 모두 forward token에 포함하지만 loss는 출력 토큰에만 계산하도록 한다. 출력에만 supervision을 준다는 뜻이다. 따라서 target token 수만으로 예상한 것보다 처리할 토큰은 훨씬 많다.

모델은 다음 요청을 받을 때 이전 대화를 다시 구성한 prompt를 읽는다. 이 prompt가 직전에 기록한 출력들을 그대로 이어 붙인 문자열과 항상 같지는 않다. 그래서 raw output을 길게 이어 붙여 학습하면 실제 실행에서 모델이 받지 않았던 입력으로 학습할 수 있다. S1은 각 호출에서 서버에 전달된 prompt와 출력의 token ID를 보존하고, 출력 토큰에만 supervision을 적용한다.

Token ID를 tokenizer로 다시 문장으로 바꿔 입력 형식을 확인하는 작업과, 31B 모델에 LoRA를 적용해 실제로 학습하는 단계는 남아 있었다. 이미 설계·분석에 활용한 과제 중 일부를 학습용으로 배정했다. 이 과제들은 독립적인 성능 평가에서는 제외한다. X40과 모델을 실행하지 않은 25개 과제 holdout은 학습에서 제외했다. S1 안에서 loss를 확인하려고 나눈 6개 과제는 코드 수정 성능을 확인할 holdout과 별개다.

호스트에서 끝까지 실행되는지부터 확인하려고 기준 번들에 모든 값이 0인 rank-16 adapter를 붙여 제출했다. 제출 후 약 25분 만에 오류가 났고 **이 시간에는 대기도 포함된다.** 원인은 모른다. 새로 확인한 [운영진 답변][d751339]은 같은 시기의 플랫폼 장애를 인정하고 영향받은 제출을 다시 실행하겠다고 했다. 하지만 우리 실패가 그 장애 때문이라고 연결해 줄 로그는 없다. 완주 여부, adapter 활성화, 학습 처리량, 수정 성능은 별개의 질문이다. 학습한 adapter의 성능 비교는 아직 하지 않았으며 큰 규모의 학습 투자도 계속 보류하고 있다.

작은 모델로 바꾸면 같은 시간 안에 더 많은 작업을 할 가능성도 있지만, 한 번의 응답에서 내는 수정안의 질은 따로 비교해야 한다. 같은 기준 설정의 로컬 비교에서 12B는 11/44, 31B는 17/44를 해결했다. 이 설정에서 얻은 결과다. USD 10,000의 E2B/E4B 보너스도 있지만, 보너스 대상이 되려면 그 제출을 팀의 최종 제출 두 개 중 하나로 골라야 한다.

**10월 23일 09:01 KST**, 기준 번들의 모델을 E4B로 바꾸고 출처와 변경 사항을 밝힌 버전을 제출했다. 확인한 기록은 **PENDING**이다. 날짜가 명시된 작은 모델 순위 스냅샷에서는 최고 Public 점수가 0.06이었다. 새 제출은 아직 점수가 없으며, 최종 제출로 선택하기로 한 것도 아니다.

## 12. 1편의 세 가지 시나리오를 다시 보면

1. **모델보다 도구 사용과 작업 순서가 문제인 경우.** 초기의 반복, 잘못된 호출, context 오류가 이 경우에 해당할 수 있다. 길이를 제한한 thinking과 주최 측 수정이 특정 비교에서는 도움이 됐다. 다만 전체 이력에서 각각 얼마나 기여했는지 분리해 측정하지는 못했다.
2. **작업 절차는 동작하지만 수정 오류가 반복되는 경우.** 실패한 패치 중 reference fix와 같은 파일을 건드린 것이 많았다. 그렇다고 원인 위치를 잘못 찾은 것인지, 요구사항을 놓쳤는지, 모델의 능력이나 시간이 부족했는지 구분되지는 않는다. 한정된 사례에서 작은 변경으로 해결할 단서를 찾아봤지만 바로 적용할 방안은 얻지 못했다.
3. **로컬의 개선이 낯선 과제에서는 유지되지 않는 경우.** 과제 모집단과 절차가 다르고, 로컬과 호스트에서 관찰한 우열이 달라진 경우도 있다. 같은 파일의 호스트 점수도 변했다. 로컬 개선을 주장할 때 조건을 함께 밝혀야 하는 이유다. 로컬에서 더 푼 수를 비공개 과제의 해결 수로 환산할 관계를 구한 것은 아니다.
